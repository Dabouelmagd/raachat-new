# تأمين SSH على السيرفر المشترك — ورقة تسليم للمطوّر

**الحالة: الجزء العاجل اتعمل (fail2ban شغّال ومتحقَّق ١٩ أكتوبر ٢٠٢٦). الباقي تحسين إضافي، وداليا سلّمته لمطوّر.**

السيرفر Hetzner `ubuntu-4gb-fsn1-1` (Ubuntu 26.04 LTS) و**مشترك**: عليه رع شات (`/opt/rachat`) ومشاريع تانية. أي تغيير في `sshd` بيأثر على **كل** طرق الدخول لكل المشاريع.

---

## ١) اللي اتعمل ✅

`fail2ban` 1.1.0 مثبّت ومفعّل (`systemctl enable --now fail2ban`). الـjail بتاعة `sshd` اشتغلت **بلا أي إعداد** لأن أوبونتو ٢٦ على journald و`fail2ban` لقى `_SYSTEMD_UNIT=ssh.service` لوحده.

**الفحص الإيجابي وقت التثبيت:** `Total failed: 48` و`Currently banned: 6` في أول ٢٠ ثانية — يعني بيقرا اللوج فعلًا والهجوم شغّال وقتها.

الحالة في أي وقت:

```
fail2ban-client status sshd
```

---

## ٢) السبب — هجوم تخمين مستمر

تخمين كلمة سر على **root** من عناوين كتير ومتغيّرة، ظاهر في `journalctl -u ssh`. مكتشف في ١٨ أكتوبر أثناء تشخيص عطل تاني.

---

## ٣) 🔴 الفخّ — الحالة اللي لازم تتفهم قبل أي تعديل في `sshd`

الفحص القبلي (١٩ أكتوبر) طلّع:

| الحقيقة | القيمة |
|---|---|
| `PermitRootLogin` | `yes` |
| `PasswordAuthentication` | `yes` |
| مستخدمون غير root (UID ≥ 1000) | **مفيش ولا واحد** |
| مفاتيح في `/root/.ssh/authorized_keys` | **٢** — تعليقاتهما `github-actions-homeme` و`github-actions-deploy` |
| دخول بمفتاح في ١٤ يوم | ٢١ |
| دخول بكلمة سر في ١٤ يوم | **٥٠** |

**الاستنتاج الحاسم:** المفتاحان الموجودان بتاعان **أتوميشن GitHub Actions** (مشروع تاني — رع شات بينشر بإيد داليا مش من CI). و**داليا بتدخل بكلمة سر**، مالهاش مفتاح خاص بها على السيرفر.

**فـ`PermitRootLogin prohibit-password` أو `PasswordAuthentication no` النهاردة = داليا تتقفل برّه السيرفر بالكامل** (مفيش حساب تاني تدخل بيه)، والأتوميشن هي اللي تفضل داخلة. الرجوع ساعتها من كونسول Hetzner بوضع الإنقاذ بس.

وعناوين داليا **متغيّرة كل دخلة** (إنترنت موبايل)، فتثبيت عنوان في قايمة بيضا مش حل.

---

## ٤) الترتيب الآمن للباقي

**لازم بالترتيب ده بالظبط. الخطوة ٤ قبل الخطوة ٣ = قفل.**

### ١. مفتاح لداليا — يتولّد **على جهازها** مش على السيرفر

```
ssh-keygen -t ed25519 -C "dalia-main"
```

> المفتاح الخاص (`id_ed25519`) عمره ما يتحرّك من جهازها ولا يتلزق في أي مكان. اللي بيتنقل هو `id_ed25519.pub` بس.

### ٢. تثبيت المفتاح العام على السيرفر

من جهازها (ماك/لينكس):

```
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@<السيرفر>
```

ويندوز (PowerShell) مافيهوش `ssh-copy-id` — الطريق البديل إضافة سطر `.pub` لـ`/root/.ssh/authorized_keys` بـ`>>` (إضافة مش استبدال — استبدال بيمسح مفتاحَي الأتوميشن ويوقّف نشر المشروع التاني).

### ٣. 🔴 التحقّق — في نافذة تانية والأولى **مفتوحة**

```
ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no root@<السيرفر>
```

لازم يدخل **بلا أي سؤال عن كلمة سر**. ولو طلب أو رفض — **وقوف**، والجلسة الأولى تفضل مفتوحة لتصليح الوضع.

### ٤. وبعد نجاح ٣ بس — إيقاف الدخول بكلمة السر

`prohibit-password` مش `no`: root يفضل يدخل **بالمفتاح**، والباسورد يترفض. (`PermitRootLogin no` بيتطلّب حساب sudo مستقل، وهو مش موجود.)

```
sshd -t
```

يتعمل **قبل** أي `reload` — إعداد مكسور + reload = خدمة SSH مش بتقوم.

---

## ٥) ⚠️ حاجة تانية لقيناها ومالمستهاش — GitHub Actions عندها root

مفتاحا `github-actions-*` في `/root/.ssh/authorized_keys` معناهما إن وظيفة CI بتاعة مشروع تاني بتدخل السيرفر المشترك **كـroot**. فأي وظيفة فيه — أو أي حد يقدر يعدّل ملف وظيفة فيه — بينفّذ أي حاجة كـroot على السيرفر اللي عليه مشاريع داليا كلها بما فيها رع شات.

ده أخطر من تخمين الباسورد على المدى الطويل. التضييق المعتاد: مستخدم محدود الصلاحية بدل root، أو `command=` في `authorized_keys` تحصر المفتاح على أمر النشر وحده.

**مالمستهوش عن قصد:** المفتاح بتاع مشروع تاني وشيله بيوقّف نشره. قرار داليا.

---

## ٦) ملحوظة تشغيلية

`fail2ban` بيحجب ١٠ دقايق بعد ٥ محاولات فاشلة — فالغلط المتكرر في كلمة السر بيحجب صاحبه هو كمان. فك الحجب:

```
fail2ban-client set sshd unbanip <العنوان>
```
